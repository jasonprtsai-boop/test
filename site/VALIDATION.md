# 驗證狀態

更新日期：2026-10-19

| 項目 | 狀態 | 證據 | 邊界 |
|---|---|---|---|
| Python 單元／整合測試 | 通過 | Python 3.14.8 下 174 項測試在 `ResourceWarning` 視為錯誤下通過；涵蓋引擎逾時、YOLO 推論逾時終止、AI 著法二次合法性、局史重播、並行快照、磁碟失敗回復、預檢關閉、Waitress 設定／生命週期與本機控制邊界 | 不連接 TM5-700 |
| Python 編譯檢查 | 通過 | `compileall` 通過 | 不代表執行期硬體正確 |
| Python 套件相依性 | 通過 | Python 3.14.8 的 `.venv` 依照 `requirements.lock` 安裝，`pip check` 無衝突 | 只涵蓋目前 Windows x86-64 環境 |
| HTTP 伺服器 | 程式與啟動驗證通過 | UI 與 TMvision receiver 已由 Werkzeug 開發伺服器改為 Waitress 3.0.2；明確設定 worker 數、proxy header 清理及關閉流程 | 仍是未加密 HTTP，不得直接暴露公網；長時間 SSE 與現場網路待運轉驗證 |
| 玩家頁瀏覽器流程 | 通過 | Chrome：四種模式選項、玩家執紅開局、紅黑控制者顯示、提示面板與狀態文字正確；`render_game_to_text` 與 console 均無錯誤 | 使用 Fake adapters，不移動真機；AI 對 AI 的逐步硬體流程由服務整合測試驗證 |
| Pikafish 提示／WDL | 程式驗證通過 | 2026-09-25 執行檔實測可回傳三條 MultiPV、評分、PV 與 WDL；提示錯誤不會結束棋局或觸發 Robot | WDL 是引擎模型估計，不是保證勝率；真機 UI 操作待現場驗證 |
| 紅黑控制與 AI 對 AI | 程式驗證通過／真機待驗 | 狀態明確保存紅黑控制者與行棋方；AI 對 AI 在 `ENGINE_READY` 前 Robot 呼叫為 0，且一次確認只執行一步 | 首版刻意不提供無人連續機械對弈 |
| 監控頁瀏覽器流程 | 通過 | Chrome：revision、階段、影像狀態與 Pose freshness 正確同步；無 JavaScript warning/error | 假資料不包含實際影像檔，因此不重複判定影像品質 |
| 對局保存與續局 | 程式驗證通過／真機待驗 | 同局沿用相同 game folder；新局建立新 folder；恢復前重新拍攝；保存盤面、實際一步玩家著法與 pending AI move 分支均有自動測試 | Fake adapters，不連接或移動 TM5-700 |
| 以目前棋盤開始 | 程式驗證通過／真機待驗 | 玩家頁可選玩家顏色與目前回合；後端重新拍攝並驗證盤面後建立新 game folder；玩家回合先檢查是否仍有合法著法且不移棋，AI 回合才計算並送出著法 | 新基準不含舊局著法歷史；真機仍須驗證雙視角拍攝與 UI 操作 |
| 連線穩定度 | 現場確認通過 | 使用者於 2026-10-12 確認已解決 | 回歸紀錄未隨 Git 保存 |
| 雙視角影像流程 | 現場確認通過 | 使用者於 2026-10-12 確認已解決 | 回歸影像與量測未隨 Git 保存 |
| YOLO `best.pt` | 已具備 | 程式固定讀取專案根目錄 `best.pt`，檔案已納入版本控制 | 模型品質仍以現場資料與實際推論為準 |
| YOLO 程序隔離與逾時 | 程式與實際模型驗證通過 | 模型載入與推論在可終止子程序執行；Python 3.11.9 與 3.14.8 對同一組 2592×1944 封存 V1/V2 分別輸出 33／13 個 detections，類別、信心與座標逐值一致，子程序正常關閉 | 尚未用故意卡死的真實 GPU／驅動故障驗證，只以逾時替身確認強制終止路徑 |
| RX／RY／RZ 到點判定 | 程式驗證通過／新姿態真機待驗 | 固定姿態已更新為 `(-180, 0, 80)`；XYZ 與三個姿態角均須到點且穩定，含 ±180° 跨界測試 | 新姿態尚未在 TM5-700 執行完整對局驗證 |
| 新棋盤 XY 矩陣 | 真機巡檢通過／已簽核 | 2026-10-13 完成全部 90 點巡檢；CSV 保存 90 筆目標與實際 Pose，最大 XYZ 誤差 `0.024 mm`；`board_coordinates_verified=True` | P90 記錄後的長連線曾發生 `WinError 10053`，不影響已保存的 90 點座標量測；每次正式啟動仍須通過動態預檢 |
| 執行期影像保留上限 | 不實作 | 使用者於 2026-10-12 明確選擇不自動刪除 | 長期運行時需由操作員自行管理磁碟空間 |
| 磁碟寫入餘量 | 程式完成 | 啟動預檢要求執行資料磁碟至少保留 1 GiB；每次動作前仍先寫安全快照 | 不會自動刪除舊局，操作員仍需管理容量 |
| 真機啟動鎖 | 程式完成 | 預設 `hardware_enabled=False`；每次程序必須明確設定 `TMCHESS_HARDWARE_ENABLED=1` 才能進入真機預檢 | 不會自動判定現場是否有人或急停是否可用 |
| Base／TCP 啟動核對 | 程式完成／人工現場確認 | `/monitor` 每次程序啟動要求操作員核對 `RobotBase / NOTOOL`，未確認不執行動態預檢 | TMflow 1.82.51 尚無本專案已驗證的自動查詢指令，因此不是自動讀值證據 |
| 本機控制 API 邊界 | 程式與 API 測試通過 | 變更狀態的 POST 要求 JSON 與精確 localhost Origin；跨來源、缺少 Origin、非 JSON 及不需要啟動碼的同來源流程均有回歸測試 | 已依操作需求移除啟動碼與登入；本機同來源程式可送出控制請求，不能直接暴露公網 |
| 安全快照耐損毀 | 程式測試通過 | `game.json` 使用唯一暫存檔、flush/fsync、程序內序列鎖及原子替換；6 執行緒共 90 次保存無損壞。最新檔損壞時使用備份並鎖定，schema 3 缺安全旗標直接 fail-closed | 無法修復兩份都損壞的盤面資料，只能由操作員確認停機後建立新基準 |
| 保存失敗 API 行為 | 程式與 API 測試通過 | 建立／保存失敗回傳 JSON 503，不保留 busy；安全停止確認無法落盤時恢復動作鎖，玩家頁保留傳輸錯誤直到下一次命令 | 實際磁碟完全損壞時仍無法保證資料落盤，只能阻止系統誤認成功 |
| Pillow 影像依賴 | 更新並驗證 | 直接依賴與 lock 均升級為 12.3.0；`pip check` 與 JPEG 接收測試通過 | 仍須隨官方安全公告維護 |
| 落子箱滿載容量 | 使用者接受不測 | 開口尺寸與單顆散布幾何已通過單元測試；2026-10-13 明確取消滿載測試要求 | 不代表最壞情況堆高已驗證；不再阻擋開始 |
| 停止、關閉與斷線後狀態 | 程式驗證通過／真機待驗 | 拍照與落子前先持久化動作鎖；停止、程序關閉、移動中斷線或吸盤關閉失敗均保留鎖；動態預檢不會自行清除，須人工確認 Robot 已停止 | 已接受的 Robot 低階命令不能由網站撤回，仍須實體急停 |
| 吸盤失敗後重新落子 | 程式驗證通過／真機待驗 | 重試前先辨識盤面；只在仍為落子前盤面時重播同一著法；棋盤取放與重試均固定 `Z=288`，不再額外下降 | 無真空／有無棋感測器，是否吸附成功仍由影像與人工判斷；新高度仍須真機低速回歸 |
| 對局結束與局史 | 程式驗證通過 | AI 回傳無著法判定敗方；每次引擎查詢從初始盤面重播所有已提交 UCI，並驗證重建盤面與行棋方完全一致 | 從「目前棋盤」建立的新局只能保有該基準之後的歷史；象棋特殊裁定仍以 Pikafish 實作為準 |
| 單程序硬體互斥 | 程式完成 | 網站與新點位工具共用 `runtime/tm5-hardware.lock` | 根目錄舊實驗程式未接入此鎖，仍須人工避免同時執行 |
| 雙視角身分 | 程式修正完成／現場回歸待驗 | 現場紀錄確認兩個節點都上傳 `2592×1944`；正式接收器已恢復 TMflow 序列順序（第一張 V1、第二張 V2），並新增同解析度雙張測試 | 正確性依賴 TMflow 兩個 External Image Processing 節點維持 V1→V2 的序列順序；流程拓撲變更後必須重驗 |

## 不在目前範圍

- 公網部署與企業級身分系統：UI 仍只綁定 localhost；不得直接改成區網或公網服務。
- NNUE 商業授權評估：本專題不作商業使用或對外散布。
