# TM5-700 中國象棋機器人網站

本目錄是獨立的新網站。它不會載入或修改根目錄的實驗結果；新對局會建立 `site/runtime/games/<game-id>/`，同一局的狀態、照片與辨識結果都直接保存在該資料夾，不再建立每次拍攝的子資料夾。全新對戰與同場重建盤面基準會產生新的 `game-id`；重新開啟網頁或成功恢復同一片段不會另建資料夾。同場的不同片段以 `battle_id` 關聯，彙整至同一本 Excel。

完整驗證邊界記錄於 `VALIDATION.md`，第三方技術查證記錄於 `KNOWLEDGE.md`。

照片會隨紀錄匯出，自動整理至 `site` 目錄下與 Excel 同名的資料夾，例如 `site/玩家名稱_2026-10-28_15-18-18_2b8c3903/`，不再增加日期子目錄，包含原圖與 YOLO 標註圖，同場各片段合併保存。照片匯出位置為紀錄根目錄的上一層；Excel 仍保存在原本的日期分類中。原始 `runtime/games` 資料保留供影像 API 與續局使用；照片整理為額外副本，會增加磁碟用量。已存在且未變更的照片不會重複複製。
2026-10-19 的錯誤隔離、斷線恢復與測試範圍請見 `RESILIENCE.md`。玩家與監控頁現在以短請求更新狀態，斷線自動重試狀態查詢；控制命令逾時不會自動重送。
整套系統檢查與本次修復見 `SYSTEM_AUDIT.md`；常見異常、處置與舊紀錄重新匯出方法見 `OPERATIONS.md`。
最新的 2026-10-20 深度檢查、停止競態與續局資料驗證修復見 `DEEP_AUDIT_20261020.md`。

## 目前完成範圍

- `/`：專題、系統流程、實測成果與入口。
- `/player`：提供「偵測目前棋盤」與「從頭開始」兩個入口；標準開局支援玩家執紅、玩家執黑、逐步確認的 AI 對 AI，以及雙人分析四種模式。
- 人類控制的回合可取得 Pikafish 三條候選路線與紅勝／和棋／黑勝估計；提示只讀取盤面，不會建立 pending move 或命令機械手臂。
- 「偵測目前棋盤」整合舊續局與目前棋盤入口，預設核對棋譜並恢復同場，也可明確選擇重建基準或開始全新對戰。
- `/monitor`：雙視角影像、六軸 Pose、動作、例行檢查、Base／TCP 與異常停機人工確認。例行檢查顯示本次 Base／TCP 確認、影像服務、引擎、機械連線及磁碟空間；其他已通過項目收進「其他檢查項目」，未通過項目全部展開，底層安全檢查仍完整執行。
- 新對戰可自訂名稱，Excel 自動附日期、時間與識別碼；玩家頁及監控台顯示實際儲存位置與更新狀態，監控台可下載。同場紀錄保存於 `site/對局紀錄/整場對戰/`。
- 系統執行紀錄固定保存於 `site/系統紀錄/system.log`，單檔 10 MiB、保留 5 份輪替檔，方便定位拍攝、引擎、Robot 與匯出錯誤。
- `127.0.0.1:8000`：UI、遊戲 API 與 SSE。
- `0.0.0.0:5000/api/vision/tmvision/detect`：只接受設定 Robot IP 的 JPEG multipart upload。
- 單一 `GameService` 與單一背景工作佇列。

真機動作開關預設開啟，啟動後會進入真機動態預檢；可設定環境變數 `TMCHESS_HARDWARE_ENABLED=0` 關閉。新姿態平移後的 90 點矩陣已於 2026-10-13 完成真機巡檢並簽核。操作員仍須在 TMflow 畫面核對 `RobotBase / NOTOOL`，再於 `/monitor` 按確認。網站停止會阻止尚未送出的後續命令，但不能撤回控制器已接受的低階運動，也不能取代實體 Emergency Stop。

動態預檢只在網站啟動後於背景完成一次。玩家頁會在預檢期間停用「開始」，不會在訪客操作時重新執行整套測試。玩家執紅時，按下開始會以標準開局盤面直接進入玩家回合，直到玩家走完並按「玩家完成」才啟動雙視角、YOLO、Pikafish 與機械手臂；Pikafish 執紅時則先拍攝並驗證初始盤面。AI 對 AI 固定採逐步模式：每一步只先計算並停在 `ENGINE_READY`，必須由操作員按「確認並執行引擎著法」才會送出該步機械命令，不提供無人連續執行。

雙人分析模式由人類控制紅黑雙方，每步仍以雙視角辨識並由 Pikafish 驗證合法性，但不產生 AI 機械落子。局勢面板的 WDL 是引擎自我對弈模型對目前局面的估計，不是對真人勝率的保證。

## 對局保存與續局

瀏覽器關閉或網頁連線中斷、但後端仍在執行時，重新開啟 `/player` 會取得同一份即時狀態，不需要重新開始。後端重啟或辨識失敗後，使用「偵測目前棋盤」，並選擇「目前棋盤的用途」：

| 用途 | 行為 | 紀錄方式 |
| --- | --- | --- |
| 恢復同一場對戰（預設） | 有完整棋譜時重新拍攝核對，沿用保存的行棋方；可唯一確認的合法玩家走子會補交 | 沿用原 `game-id`、棋譜及 Excel |
| 同一場對戰，重新建立盤面基準 | 依選定的玩家棋色及目前回合建立新基準；無法確認的中間棋步標示為歷史缺口 | 新 `game-id`、同一 `battle_id`，繼續更新同一本 Excel |
| 開始全新對戰 | 以現場盤面建立全新對戰，依選定的棋色及回合開始 | 新對戰編號與 Excel |

預設恢復若沒有上一場可接續對戰，會建立新對戰；若上一場仍未結束但缺少完整可重播棋譜，會建立同場新基準並保留片段關聯。已結束的對戰不會自動接續。完整棋譜必須包含初始盤面、初始行棋方與 UCI 著法，且重播後能精確得到保存盤面與行棋方；盤面核對失敗時不會直接覆蓋舊歷史。

現場盤面才是正確基準、但已無法對上保存棋譜時，可明確選擇「同一場對戰，重新建立盤面基準」。舊資料仍保留，不推測遺失棋步；長將及重複局面等依賴歷史的判斷只能從新基準起算。偵測會接續遊戲流程，並非只有拍照預覽；建立基準時選擇 AI 回合，辨識成功後會進入 AI 計算及動作流程。

schema 3 缺少明確的 `motion_state_uncertain` 布林值會視為快照損壞；舊快照若中斷於拍攝、驗證、移動、停止或錯誤階段則鎖定真機。若建立新基準時所選玩家已無合法著法，系統會標記對局結束。

若程式在 AI 落子途中中斷，續局不會直接重播機械動作：已完成的著法會在拍照確認後提交；尚未完成的著法會停在可重試狀態；盤面同時不符合落子前與預期盤面時則停止並要求人工檢查。

若後端仍在執行、但 YOLO 或 Pikafish 等非運動步驟失敗，玩家頁可使用「偵測目前棋盤」恢復同場，不必重啟網站。拍照路徑與 AI 棋步送出前都會先把「可能仍在動作」寫入 `game.json`；完成 Listen／Pose 穩定確認後才清除。若程序中斷、Robot 連線失敗或吸盤關閉命令無法確認，單純重啟不會解除鎖定。現場操作員必須先確認 Robot 已完全停止，再於 `/monitor` 明確解除；若有危險，仍須先使用實體 Emergency Stop。

吸盤沒有真空或有無棋感測器，DO 回覆只代表控制器接受輸出命令。AI 落子後不再拍照比對，動作成功返回即按預期盤面提交棋步；若實際取放失敗，請停止流程，再從現場盤面重建基準。中斷後保留的 pending move 仍須先辨識現場盤面，才可恢復或重試，避免重播已完成棋步。

對局結束的基本判斷由 Pikafish 完成：輪到一方但沒有合法著法時，該方落敗。AI 無合法著法則玩家獲勝；AI 落子後玩家無合法著法則 AI 獲勝。引擎查詢會從本局初始盤面重播 `game.json` 中所有已提交 UCI 著法，使 Pikafish 能取得重複、長將／追逐與 rule-60 所需的局史；若保存歷史不能精確重建目前盤面，查詢會拒絕執行。重新建立盤面基準時，歷史只會從該新基準起算，不能還原更早的局史。

每局資料結構如下：

```text
site/runtime/games/<game-id>/
├─ game.json
├─ R001_C001_player_move_<capture-id>_v1.jpg
├─ R001_C001_player_move_<capture-id>_v2.jpg
├─ R001_C001_player_move_<capture-id>_v1_yolo.jpg
├─ R001_C001_player_move_<capture-id>_v2_yolo.jpg
└─ R001_C001_player_move_<capture-id>_result.json
```

檔名中的 `R###` 是本局輪次、`C###` 是本局拍攝序號，用途代碼可區分玩家走子、AI 驗證、續局或重試。`game.json` 保存已提交棋盤、輪次、紅黑方、pending move、拍攝歷程與 Robot 動作歷程；`result.json` 保存該次辨識的棋盤矩陣與每格信心。執行期資料目前不會自動刪除，長期使用時需由操作員管理磁碟空間；可用空間低於 1 GiB 時預檢會拒絕開始新局，避免動作前的安全快照無法寫入。

`game.json` 保存由單一程序鎖序列化，每次使用唯一暫存檔、`fsync` 與原子替換，並保留上一版備份。建立或保存失敗時控制 API 回傳 JSON 503 並解除忙碌狀態；若「確認 Robot 已停止」無法落盤，程式會恢復安全鎖而不是只在記憶體宣告成功。

### Excel 命名與儲存位置

開始新對戰前，可在「新對戰名稱（選填）」輸入最多 40 字；空白時使用「象棋對戰」。檔名保留文字、數字、空格、連字號與底線，其他字元會替換成底線，並自動附上台灣日期時間及識別碼，避免同名覆蓋。例如：

```text
site/對局紀錄/整場對戰/
└─ 王同學練習賽_2026-10-21_14-30-00_a1b2c3d4.xlsx
```

命名只在建立全新對戰時生效；同場恢復、重建基準及程式重啟均沿用原名稱與檔案。舊紀錄沒有名稱欄位時保留原命名，可能位於 `對局紀錄/<game-id>.xlsx` 或 `對局紀錄/整場對戰/<battle-id>.xlsx`，請以頁面顯示的實際路徑為準。

玩家頁及監控台顯示目前 Excel 的完整路徑，以及建立／更新／失敗狀態；監控台提供下載。同場多次重建基準會在一本 Excel 中保留各片段，不能把片段數當成實際對戰場數。

Excel 包含「對局摘要」、「對戰片段」、「著法紀錄」、「拍攝紀錄」、「Robot動作」、「流程紀錄」、「引擎紀錄」、「辨識盤面」及各片段「棋盤履歷」。保存每步 UCI、矩陣、P 編號、Robot XY、FEN 前後、吃子資訊及耗時；引擎紀錄包含查詢用途、結果與錯誤，辨識盤面包含原始／採用盤面及逐格信心。棋盤履歷依各片段的可靠初始盤面與已提交著法重播，採紅方在下並標色起終點。無法還原的棋步與耗時不補猜，缺值區分未記錄、未取得及不適用。

Excel 由背景工作合併更新、暫存檔原子替換；被 Excel 鎖住或暫時無法寫入時，每約 5 秒重試最新快照，不重送真機命令。監控會顯示失敗與更新中，既有檔案可能仍是上一版。安全恢復仍以同步保存的 `game.json` 為準。

每次 Line 動作完成後，程式會連續檢查 XYZ 與 RX／RY／RZ；位置誤差須在 1 mm 內、各姿態角最大誤差須在 1° 內，而且連續樣本的位置／姿態變化分別不超過 0.1 mm／0.1°，達到設定樣本數後才進行下一段動作。姿態不符會逾時停止後續流程，不會被只有 XYZ 到點的回授誤判為完成。

每次取放前會先在目前 X/Y 原地抬升到至少 `Z_SAFE`，保持當前姿態；到達安全平面後才切換成固定 RX／RY／RZ，再進行水平移動。停止訊號會在每一段 Line 與吸盤命令前檢查，因此不再開始下一段；已送出的當前 Line 仍可能繼續。

## Python 3.14 環境

Windows 安裝 Python 3.14.8 後，在本目錄執行：

```powershell
$python314 = "$env:LOCALAPPDATA\Programs\Python\Python314\python.exe"
& $python314 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements.lock
```

`requirements.txt` 保存直接依賴，`requirements.lock` 保存本次 Python 3.14.8 驗證通過的完整版本集合。網站由 Waitress 提供 HTTP 服務，不再使用 Werkzeug 開發伺服器。
若 Python 已正確註冊到 Windows launcher，也可用 `py -3.14` 取代 `$python314`。

啟動：

```powershell
$env:TMCHESS_HARDWARE_ENABLED = "1"  # 只在有人值守且完成現場安全檢查時設定
.\.venv\Scripts\python.exe app.py
```

未設定環境變數時，真機動作開關預設開啟；設定為 `0` 時，網站可啟動與檢視，但真機預檢不會通過。瀏覽器開啟 `http://127.0.0.1:8000`，先到 `/monitor` 核對並確認 Base／TCP，再操作玩家頁。TMflow 的 External Image Processing URL 使用本機區網 IP 與 port `5000`，路徑固定為 `/api/vision/tmvision/detect`；不要填 `127.0.0.1`。

## Pikafish 連接

產品程式使用真正的 `PikafishEngine`，不是測試替身。資料流為：

```text
雙視角 YOLO 盤面
→ 10×9 棋盤矩陣
→ Pikafish FEN
→ UCI position / go
→ bestmove
→ pending move
→ 機械手臂移動及拍照驗證
→ 驗證成功後才提交盤面
```

所需檔案位於 `..\engine_bin\`：`pikafish.exe`、`pikafish.nnue`、引擎與權重授權文件。GUI、開局庫、原始碼與其他 CPU 版本不會被網站載入。

單獨驗證真實引擎輸入／輸出及應用程式接線：

```powershell
.\.venv\Scripts\python.exe -m unittest tests.test_engine -v
```

此測試會把標準開局盤面傳給實際執行檔、取得著法，再請引擎確認該著法是否合法；不連接或移動 TM5-700。

## 跨輪盤面比對

對局只維護一份已提交棋盤作為基準：玩家先手從標準開局建立，AI 先手從首次雙視角辨識建立；玩家合法走子或 AI 手臂動作成功完成後更新基準。

已有確認盤面時，若新影像能唯一判定移動棋子的起點與終點，系統會將該步套用到上一盤面，其餘誤辨識格沿用上一盤面。包含漏棋、錯色、多棋及多格錯誤；不再受「一格／低信心／同色」限制，但必須符合：

- 已能唯一判定一枚棋子的起點與終點。
- 差異格不在這一步的起點或終點。
- 起點清楚變空、終點辨識為該棋子，且沒有第二組可成立的候選走子。
- 修正後盤面通過結構檢查，玩家走法通過 Pikafish 合法性檢查。
- AI 驗證時，該唯一走法必須與 pending move 完全相符。

端點不清楚、吃子／落子位置不符、同時移動兩枚棋子、多個候選或非法走法仍會暫停。新建局沒有有效基準時仍嚴格驗證；沒有走子證據的續局全盤核對沿用原本較嚴格的局部修正。修正格位、原觀察類別與歷史類別保存於拍攝紀錄／Excel，原始照片、YOLO 圖及觀察 JSON 留存。影像噪音與真實物理改變若無法區分仍有誤判風險，現場一次只移動一枚棋子。

## 真機設定與啟動前檢查

以下項目已由使用者確認；工作站、工具、棋盤或場地配置改變後必須重新簽核：

### 9×10 棋盤點位真機巡檢

先只顯示 90 點路徑，不連接機械手臂：

```powershell
.\.venv\Scripts\python.exe tools\verify_board_matrix.py
```

建議先測第一點並逐點確認。棋盤可保留正常平放的單層棋子，但不可有堆疊、翹起的棋子或其他異物：

```powershell
.\.venv\Scripts\python.exe tools\verify_board_matrix.py --execute --start-point 1 --end-point 1 --step-confirm --allow-below-configured-safe-z
```

第一點確認後，再把 `--end-point 1` 改為 `--end-point 90`。流程為安全高度進場、在 Z=380 跨點、Z=340 接近、低速下降至 Z=300、停留三秒、回升至 Z=380。結果逐點寫入 `runtime/calibration/*.csv`，包含目標／實際 Pose 與 XYZ 誤差。

棋盤表面為 Z=280、棋子厚度為 10.3 mm，因此棋子頂面約為 Z=290.3；巡檢最低點 Z=300 的名義間隙約為 9.7 mm，扣除目前 2 mm 高度容差後仍約為 7.7 mm。此判斷只適用於正常平放的單層棋子。

注意：Z=380 低於正式 `Z_SAFE=525`，因此真機模式必須明確加入 `--allow-below-configured-safe-z`。這只表示操作員接受該次巡檢路徑，不會修改正式對局的 `Z_SAFE`。

`Ctrl+C` 只會停止送出後續點位，不能保證立即停止已經送給控制器的當前運動；需要立即停機時必須使用實體 Emergency Stop。

## TMflow 1.82.51 限制

Listen Server 仍由既有 TMflow Listen 節點啟用；網站只送出現有實測已使用的 TMSCT 指令，不改變流程拓撲。官方 External Image Processing 舊版範例標示的起點是 TMflow 1.84，因此 1.82.51 的 HTTP／Listen 行為仍須在現場重新確認，不應直接視為官方版本保證。

若畫面曾出現 `$CPERR,2,F1`，其意義是 TMflow 當下尚未進入 Listen 節點，不是座標或 checksum 錯誤。網站會重新連線並以唯讀 Pose 查詢等待最多 12 秒，確認 Listen 就緒後才送出拍照或移動命令。若仍逾時，請確認 TMflow 專案正在執行、流程沒有停在 Vision／其他節點，且確實會走回 Listen；不要略過錯誤或直接重送移動命令。

TMvision 上傳成功後，receiver 會回傳 TMflow 可解析的 `message/image_w/image_h/annotations` detection JSON，讓流程由 V1 前往 V2；`capture_ok` 只代表影像已安全接收，不代表 YOLO 盤面辨識成功。V1 與 V2 各自等待最多 30 秒，兩張都到齊後才執行真正的 YOLO 融合。

V1／V2 依 TMflow 圖中的上傳順序識別：第一個 External Image Processing 節點為 V1，收到成功回覆後才會執行第二個節點並上傳 V2。現場兩個節點目前都輸出 `2592×1944`，因此不能用解析度區分視角；V1 的既有 `2048×1536` 校正座標會依實際影像尺寸等比例換算。每次 capture 只接受兩張影像，未啟動拍攝或第三張以上仍會被拒絕。YOLO 載入時也會核對模型類別集合與程式盤面定義，類別缺少或多出時不會進入對局。

YOLO 模型常駐於獨立程序，模型載入與每次推論的牆鐘上限預設都是 60 秒。超時、停止或程式關閉會終止該程序，避免原生 ML runtime 卡住整個工作流程；下一次合法拍攝會重新建立乾淨的推論程序。

YOLO 正常盤面使用 `0.25` 信心門檻。若融合結果違反象棋棋子數量硬上限，系統才以 `0.10` 取得同一格的其他候選類別，並只允許同色、未超額的候選取代最低可信超額類別；不會放寬棋子上限、補空格或跨格修正。無法安全修正時仍會停止，不會把異常盤面交給 Pikafish。


### 2026-10-21：現場棋盤模式

「從頭開始」與「偵測目前棋盤」共用人對機（玩家固定紅方）、AI 對 AI、雙人分析三種模式。新現場對戰或重建基準可指定紅方／黑方回合；AI 對 AI 每步仍需確認，雙人分析由人類走雙方。恢復完整棋譜時沿用保存的模式與回合，包含舊版玩家執黑的對戰；不會因畫面選項覆寫歷史。選人對機黑方回合時，辨識後會進入 AI 自動落子流程。
