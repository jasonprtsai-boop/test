# Decision log

## 2026-10-19 — 依操作需求移除一次性啟動碼

- **Decision:** 移除啟動碼產生、Flask operator session、解鎖／鎖定 API 與監控頁輸入欄位；保留 JSON、精確 localhost Origin、真機環境變數、每次啟動的 Base／TCP 人工確認、異常停止確認與動態預檢。
- **Reason:** 操作端明確要求取消這個額外步驟；啟動碼不是機械安全聯鎖，移除後不應連帶放寬實體動作條件。
- **Alternatives:** 保留啟動碼或改成固定密碼都不符合目前操作需求；完全移除 Origin 與真機預檢會不必要地擴大風險，未採用。
- **Evidence:** Python 3.14.8 下 174 項測試、`compileall`、`pip check` 與三份 JavaScript 語法檢查通過；API 回歸測試證明同來源 JSON 不需啟動碼，跨來源、缺少 Origin 與非 JSON 仍被拒絕。
- **Trade-off:** 任何能在允許的本機網站來源執行程式的人，都能在其他真機安全條件通過後送出控制請求；系統沒有獨立的本機操作員身分驗證，不得直接暴露至公網。

## 2026-10-16 — Python 3.14.8 與 Waitress 成為預設執行環境

- **Decision:** 將預設 Python 從 3.11.9 升級為 3.14.8，鎖定安裝工具與完整套件版本；UI 與 TMvision receiver 改由 Waitress 3.0.2 提供服務，不再使用 Werkzeug 開發伺服器。
- **Reason:** 3.11.9 已落後多個安全修補，且 Werkzeug 官方不支援把開發伺服器用於正式運行。
- **Alternatives:** 留在 3.11.9 只更新應用套件無法取得 CPython 後續安全修補；直接升級到尚未驗證的 3.15 會增加原生 AI 套件相容風險，均不採用。
- **Evidence:** Python 3.14.8 下 175 項測試、`compileall`、`pip check`、JavaScript 語法檢查與真實 Pikafish 通過；同一組封存 V1/V2 的 YOLO 輸出與 3.11.9 逐值一致（33／13 detections）。Waitress 建立、主流程與關閉生命週期另有單元測試，實際服務的 UI 回應 200、Vision 接收路由對錯誤方法回應 405。
- **Trade-off:** 升級需要重建虛擬環境；現場 TM5-700、TMvision 網路與長時間 SSE 仍需有人值守驗證。舊 3.11 環境暫存於 `.venv311-backup`，不屬版本控制內容。

## 2026-10-15 — 恢復、推論與關閉流程採可終止且可證明的邊界

- **Decision:** schema 3 快照強制保存布林動作狀態，舊版在不安全階段缺旗標時自動鎖定；只有能從初始盤面完整重播到目前盤面的局史才可續局。快照保存以程序內鎖、唯一暫存檔、原子替換與 Windows sharing-violation 重試序列化。同步保存失敗回傳 JSON 503、解除 busy，安全停止確認失敗則恢復動作鎖。
- **Runtime isolation:** YOLO 模型與推論移至持久化子程序；模型載入與每次推論均有牆鐘逾時，停止或關閉可終止子程序。預檢執行緒受生命週期追蹤，未結束前不釋放 Robot／engine 資源。
- **Reason:** 稽核重現了缺少安全旗標的 `ROBOT_MOVING` 快照可解除鎖、同步磁碟錯誤會永久卡住控制、並行保存會在 Windows 互相替換失敗，以及原生 YOLO 呼叫沒有可取消上限。
- **Alternatives:** 只加 thread timeout、沿用固定 `.tmp`、缺旗標預設安全、缺局史只傳目前 FEN（均不能安全終止或維持象棋歷史規則，淘汰）。
- **Trade-off:** YOLO 首次預檢需建立一個子程序，舊版不完整快照不能直接續局而必須「從目前棋盤開始」；換取卡死可終止、恢復語意可驗證，以及持久化失敗後可再次操作。
- **Evidence boundary:** 172 項測試、ResourceWarning 嚴格模式、實際 `best.pt` 隔離載入與 2592×1944 封存影像推論（33 個 detections）通過；本輪未連接或移動 TM5-700。

## 2026-10-15 — 引擎、快照與控制面採 fail-closed 修復

- **Decision:** Pikafish 查詢帶入完整已提交局史；任何引擎搜尋例外都終止該程序，AI bestmove 在 Robot 動作前再次做合法性查詢。`game.json` 改為 fsync 原子寫入並保留上一版，損毀時鎖定實體動作。所有控制 POST 需 localhost Origin 與一次性啟動碼建立的 operator session；真機開關預設關閉。
- **Superseded:** 一次性啟動碼與 operator session 部分已由 2026-10-19 決策取代；其餘引擎、快照、Origin 與真機開關決策仍有效。
- **Reason:** 稽核實測可讓逾時搜尋的延遲 `bestmove` 污染下一局面、可接受只通過棋子顏色檢查的非法著法；損毀最新快照原本會被當成沒有續局，控制 API 也只依賴 UI 分頁隔離。
- **Alternatives:** 清空佇列但沿用不確定狀態的引擎程序、損毀時直接忽略存檔、只隱藏操作按鈕（均不能證明安全，淘汰）。
- **Trade-off:** 啟動多一道解鎖，逾時後需重啟引擎；安全快照多佔一份 JSON 空間。換取跨請求隔離、可恢復上一版，以及控制面明確授權。
- **Evidence boundary:** 自動測試與真實 Pikafish／YOLO 本機整合可驗證；未在本輪連接或移動 TM5-700，真機完整對局仍需有人值守現場驗收。

## 2026-10-13 — 開局入口區分保存局、目前棋盤與標準開局

- **Decision:** 玩家頁提供三條明確路徑：嚴格核對後「繼續上一局」、重新拍攝後「從目前棋盤開始」、以及「從頭開始」標準開局。目前棋盤模式由操作員選擇玩家顏色與目前回合，建立新的 game folder 與盤面基準。
- **Reason:** 保存盤面與現場棋盤不一致時，舊流程只能拒絕續局並返回先手選擇，無法在不偽造歷史的前提下保留現場局面。
- **Safety boundary:** 目前棋盤模式仍須通過雙視角、棋盤結構驗證與動態預檢；選 AI 回合後才允許 AI 計算及機械動作。動作狀態未知時三種入口都維持鎖定。
- **Trade-off:** 可保留實體局面，但不延續舊局著法歷史，因此長將、重複局面等歷史型裁定從新基準起算；舊資料保留但不再作為新局狀態來源。

## 2026-10-13 — 棋盤取放高度固定為 Z=288

- **Decision:** 依現場觀察把棋盤 `z_pick` 從 290 mm 下修為固定 288 mm；一般移動與人工「重新落子」都使用同一高度，取消重試時額外下降 1 mm。落子箱高度不變。
- **Reason:** 原高度仍有少量間隙；若保留舊重試修正，重試會下降到 287 mm，不符合固定高度要求且增加碰撞風險。
- **Safety boundary:** 程式測試不連接 TM5-700；重啟服務後仍須由操作員握有急停，以低速做單點取放回歸，確認 288 mm 不接觸棋盤。
- **Trade-off:** 所有棋盤目的格放棋也同步改為 288 mm；高度一致較可預測，但仍無吸盤感測器可直接證明吸附。

## 2026-10-13 — 無吸盤感測器時採人工重新落子與固定 -1 mm 取棋修正

- **Decision:** 驗證失敗後顯示「重新落子」；先重新拍攝，只有盤面仍是落子前狀態才重播原 pending move。重播只把來源取棋高度固定下修 1 mm，放棋高度不變，重複按鈕不繼續累加下降。
- **Reason:** DO 回覆只能證明控制器接受輸出命令，不能證明棋子已吸住或放掉；現場沒有可提供閉迴路證據的真空／有無棋感測器。
- **Safety boundary:** 部分完成、棋子黏在吸盤、盤面不明或已被人工改動時不自動重播；操作員須先還原到落子前盤面。按鈕不取代實體急停。
- **Trade-off:** 可在常見的吸取高度誤差下重試，但成功與否仍依賴雙視角驗證和人工觀察。

## 2026-10-13 — 拍照路徑納入實體動作鎖，解除改由人工確認

- **Decision:** `ScriptExit()` 觸發的雙視角 TMflow 路徑與 AI 棋步都在送命令前持久化 `motion_state_uncertain=True`；只有 TMflow 回到 Listen 且 Pose 穩定時才在正常流程清除。停止、關閉或錯誤後的鎖不由一般動態預檢自動清除，操作員須在 `/monitor` 確認 Robot 已停止。
- **Reason:** Vision 節點之間包含實體移動；單次 Pose 與吸盤 DO 回覆不足以證明過去的低階動作已停止。程序關閉若先存檔再設停止，重啟會錯誤顯示安全。
- **Trade-off:** 異常中斷後多一個人工確認步驟；正常對局不增加玩家操作。

## 2026-10-13 — Base／TCP 使用每次啟動人工一致性確認

- **Decision:** 不猜測 TMflow 1.82.51 的 Base／TCP 查詢指令。操作員每次啟動在 TMflow 畫面核對 `RobotBase / NOTOOL`，再於 `/monitor` 確認；未確認不執行動態預檢。
- **Reason:** 靜態設定名稱不能證明執行中 TMflow 專案的實際選擇，但目前沒有已驗證的程式查詢介面。
- **Trade-off:** 不是自動保證，但相較只保存旗標具有可執行的啟動檢查，且不增加玩家頁複雜度。

## 2026-10-13 — 基本勝負判斷以無合法著法為終局

- **Decision:** Pikafish 輪到 AI 時回傳無著法，判定玩家獲勝；AI 著法提交後，若玩家沒有合法著法，判定 AI 獲勝。
- **Boundary:** 目前 FEN 狀態沒有完整著法歷史，因此長將、重複局面等歷史型裁定不自動宣稱完成。

## 2026-10-13 — 真機錯誤路徑採保守鎖定

- **Decision:** 每一段 Line 與吸盤命令前都檢查停止訊號；首段棋盤移動前先在目前 X/Y 原地進入至少 `Z_SAFE`，到安全平面後才切換固定姿態。移動中連線失敗或吸盤關閉無法確認時，將實體狀態標成未知並鎖住新局、重試及續局；鎖定寫入 `game.json`，不因程序重啟遺失。
- **Reason:** 網站停止無法撤回控制器已接受的命令，連線中斷也不能證明 Robot 已停或吸盤已關。繼續送命令會把未知實體狀態擴大成碰撞或重複取放風險。
- **Safety boundary:** 鎖定不能取代實體急停；重啟後動態預檢不會自行解除中斷鎖，須由現場操作員確認 Robot 已完全停止後，在監控頁明確解除。
- **Verification:** 自動測試覆蓋停止後不送下一命令、安全平面移動順序、吸盤關閉失敗與移動中 socket reset；尚未在 TM5-700 上刻意製造中斷測試。

## 2026-10-13 — 預檢新增三個不可推測的現場阻擋（後續部分更新）

- **Decision:** 新姿態後 90 點矩陣、Base／TCP 啟動時一致性機制、落子箱滿載容量分別使用獨立 fail-closed 旗標；未簽核前正式對局不可開始。
- **Reason:** 單點平移不能證明 90 點；設定檔名稱不能證明 TMflow 執行時選擇；單顆落點幾何不能證明整局多顆棋子的堆高安全。
- **Alternative:** 沿用舊簽核或把靜態設定視為執行期證據（淘汰）。
- **Trade-off:** 網站目前不能進入真機對局，但監控頁會明確列出缺少的證據，避免把未知條件誤標為安全。

後續更新：落子箱滿載改為使用者風險接受；Base／TCP 改為每次啟動人工確認。新姿態平移後的 90 點矩陣仍維持待重新簽核。

### 2026-10-13 更新 — 落子箱容量改為風險接受

- **User decision:** 不進行落子箱滿載容量與堆高測試。
- **Implementation:** 將該項改記為 `graveyard_capacity_risk_accepted=True`，不再阻擋開始；不宣稱實測通過。
- **Still enforced:** 落子箱中心、110 × 110 mm 淨開口、獨立 safe／approach／release Z、27 mm 棋子直徑、35 mm 散布半徑與 5 mm 邊界裕量仍須通過設定及幾何檢查。
- **Residual risk:** 多顆棋子堆高、反彈或靠近吸盤釋放高度的最壞情況沒有現場證據。

## 2026-10-13 — 雙視角與 AI 初始狀態建立明確身分

- **Decision:** V1／V2 以各自 JPEG 解析度識別，拒絕未知尺寸與重複視角；AI 先手的新局必須辨識成完全相同的標準初始棋盤；YOLO 模型類別集合在首次載入時必須與盤面定義完全一致。
- **Reason:** 網路到達順序不能代表相機身分；只通過一般盤面合法性不足以證明新局擺盤正確；類別索引錯配會把有效偵測轉成錯棋種。
- **Trade-off:** 更換相機解析度或模型類別後會 fail closed，必須先更新設定與重新驗證。

## 2026-10-13 — 已結束棋局不復活，並在開始頁保留結果

- **Evidence:** 現場連續五次辨識得到相同盤面，且與較早一局保存盤面完全一致；Pikafish 判定該局玩家已無合法著法。較新的標準開局存檔與現場盤面相差 23 格，因此「繼續上一局」拒絕是正確的安全行為，不是辨識抖動。
- **Decision:** `FINISHED` 對局維持不可續局，開始頁清楚顯示上一局結束原因；保存盤面不符時回報差異格數並指引使用目前棋盤模式。從目前棋盤建立玩家回合前，另由 Pikafish 確認玩家仍有合法著法。
- **Reason:** 自動選擇較舊或已結束的棋局會混淆回合與歷史，可能讓 AI 在錯誤狀態移動；原介面立即隱藏結束訊息，則讓正常的終局看起來像意外跳回首頁。
- **Trade-off:** 現場盤面若本身已是死局，使用目前棋盤模式也不會強行繼續；要開始新局必須重新擺成可玩的局面。

## 2026-10-14 — 單局平面化拍攝與分類操作紀錄

- **Decision:** 同一局照片、YOLO 標註圖、辨識 JSON 與 `game.json` 直接放在同一個 `runtime/games/<game-id>/`；檔名使用 `R###_C###_<purpose>_<capture-id>`，不再為每次拍攝建立子資料夾。
- **Observability:** `game.json` 分別保存著法、拍攝、Robot 動作與流程歷程；每局 Excel 分成摘要、著法、拍攝、Robot 動作、流程五張表，記錄矩陣／Robot 座標、FEN 前後、位置誤差、影像信心與各階段耗時。
- **Performance boundary:** 不新增拍攝、Robot 路徑或同步 Excel I/O；Excel 仍在背景合併更新。同步保存的 `game.json` 是恢復來源，Excel 失敗不得觸發 Robot 重送。
- **Compatibility:** 影像 API 優先讀取新平面檔名，仍可讀取舊版 `captures/<capture-id>/` 結構。

## 2026-10-13 — 非運動錯誤支援同程序續局

- **Decision:** 已建立盤面後發生非運動、非 pending-retry 錯誤時，立即載入同一局保存快照並在玩家頁提供「繼續上一局」；恢復前仍重新拍攝核對，不建立新資料夾。
- **Safety boundary:** 移動／吸盤狀態未知時不提供續局；pending AI move 仍走原本的重試前重新觀察流程。
- **Reason:** YOLO 或 Pikafish 暫時失敗不應強迫重開後端或建立另一局，但不能跳過實體盤面核對。

## 2026-10-12 — 每局獨立保存與安全續局

- **Decision:** 每次按「開始遊戲」建立一個 `runtime/games/<game-id>/`；同一局所有原圖、YOLO 標註圖、辨識結果與 `game.json` 均保存在其中。重新載入網頁或繼續上一局沿用原資料夾。
- **Recovery:** 後端重新啟動後只提供最新且未完成的一局。操作員須依實體棋盤指定目前輪到玩家或 AI；系統先重新拍攝核對，通過後才恢復流程。
- **Safety boundary:** 中斷時存在 pending AI move，不因使用者選擇回合而直接重播。實體盤面符合預期才提交；仍是落子前盤面時進入人工確認後的「重新落子」；其他差異一律停止。
- **Reason:** 瀏覽器或程序中斷不應強迫重新開局，但保存的軟體狀態不能取代對實體棋盤的重新確認。
- **Trade-off:** 續局會增加一次雙視角拍攝；已標記 `FINISHED` 的最新對局不提供恢復，也不向前搜尋更舊的未完成對局，避免操作員誤選錯局。
